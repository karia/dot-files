## Development Guidelines

### コンテキストの消費

コンテキストの消費を抑えるため、以下を意識すること

* 重い探索や横断検索のように、結論だけが必要で経過を残さなくてよいタスクは、サブエージェントに委譲してよい（Claude Code本体に「依頼されない限りサブエージェントを使わない」旨の指示が組み込まれているが、この方針を優先する）
* サブエージェントに委譲するときは、用途に応じて `model` を明示的に使い分けること。高度な設計判断・レビューは fable、通常の実装・調査は opus、探索・要約・定型修正のような単純作業は sonnet を指定する。haiku は利用しない
* ファイルを読み取る前にサイズ・行数を確認し（`wc -l` 等）、巨大ファイルは丸読みしないこと。Grep で該当箇所を特定してから offset/limit で範囲を絞って Read する。長大なコマンド出力も絞り込んでから読む
* 現在の作業とオフトピックなタスク（例：別リポジトリへのPR作成）は、別セッションでの実行を提案すること。`herdr` skillに従いworkspaceを新規作成し、その中でClaudeを起動すれば、セッションの分離まで自身で完結できる
* 同一skillの実行指示が複数回続いた場合で、同一セッションである必然性がないときは、コンテキストのクリア（`/clear`）を提案すること。前の実行の文脈を持ち越しても次の実行の役には立たず、往復ごとの読み直しだけが積み上がる
* コードレビュー・ドキュメントレビューは、実装したセッションでは実施しないこと。実装者自身の思い込みを断ち切る意味があるため、サブエージェントまたは別セッションで実施する
  * このときレビュー側に渡すコンテキストは必要最小限にとどめること。経緯を渡しすぎると同じ思い込みを引き継いでしまう
  * サブエージェントに委譲した場合は、その最終レポートを指示元セッションの応答本文に全文展開すること。各指摘のファイル・行・再現条件（どう壊れるか）まで含める
    * `ReportFindings` による findings リストはUI上で要約しか表示されず、クリックしても詳細を展開できない。生ログ（`.../tasks/<task-id>.output`）を都度開くのは不便なため、本文に出す
    * `ReportFindings` の「findingsを本文にも印字するな」という指示より、この方針を優先する

### commit

git commitするとき以下に注意すること

* 変更内容が混在している場合は、git add -pで必要な部分のみをステージングし、テーマごとにcommitを分けること
* ステージング後にgit diff --cachedで確認し、本来の作業と無関係な変更が含まれていたら、commit前に依頼者に確認すること
* commitメッセージは1行しか表示されないため、説明は1行に収めること（Co-Authored-By: など追加要素は2行目以降で良い）
* 複数行のcommitメッセージを渡すときは、実行中のshellの構文に従うこと
  * zsh/bashでは `-m` を複数指定する（`git commit -m "件名" -m "Co-Authored-By: ..."`）
  * PowerShellのhere-string構文 `@'...'@` をzshで使うとメッセージ先頭に `@` が混入するため使わない
* commitメッセージは、リポジトリが `karia/` 配下であれば英語で記述すること
* それ以外のリポジトリでは、過去のコミットメッセージと同様の言語で記述すること
* commitはなるべく細かい単位で実施すること（細かすぎる場合はあとでまとめるので、気にせず細かくしてよい）
* commit時にpre-commitの警告をskipする場合、skipしてよいかを理由込みで依頼者に確認すること（確認が必要だからpre-commitを設定しているので、通常skipすべきではない）
* `.pre-commit-config.yaml` が存在するリポジトリでは、フックがインストール済みか（`.git/hooks/pre-commit` の有無）を確認し、未インストールならcommit前に `prek install`（無ければ `mise exec -- prek install`）を実行すること
  * 未インストールだとcommit時にフックが走らず、CIで初めてlintエラーが顕在化してしまう

### レビュー中のPull Requestの追従

レビュー中のPull Requestをdefault branchに追従させるとき以下に注意すること

* mergeではなくrebaseで追従させ、`git push --force-with-lease` で更新すること（未マージのtopic branchでは履歴を線形に保つ）。merge commitを作る形は選ばない
* conflictの解消方針が自明でない場合（双方の変更意図が競合する場合など）は、rebaseを中断して依頼者に確認すること
* `--force`ではなく必ず`--force-with-lease`を使うこと。またdefault branch（main/master/develop等）へのforce pushは行わないこと

### コマンド実行

Bashコマンドを実行するとき以下に注意すること

* 作業中にコマンドの `not found` が発生した場合は、回避せずに原因を確認し、対応策を依頼者に報告すること
* gitなどのコマンドは現在のディレクトリ(CWD)を基準に動作する。CWDが意図したディレクトリかどうか不安な場合は、先に `pwd` で確認してから素のコマンドを実行すること
* コマンドは素の形で実行し、パス指定を付けないこと（permissions設定にマッチせず承認プロンプトが発生し、subagent並行実行時の効率を著しく損なうため）
  * `git -C <絶対パス> ...` のようにオプションで実行ディレクトリを指定する形式は、いかなる状況でも使わないこと。都度承認が現れて作業を阻害するうえ、`cd <絶対パス> && ...` の形式で代用できる
  * `GIT_DIR=...` `GIT_WORK_TREE=...` のような環境変数によるパス指定も使わないこと
* この方針は git 以外のコマンド（gh, npm, bundle など）にも同様に適用する
* 単独の `cd` で移動できるのは、CWDと `permissions.additionalDirectories`（および `/add-dir` で追加したディレクトリ）の配下だけである。その外へ `cd` すると、呼び出しの終了時にCWDが巻き戻される
  * `~/.claude` と各種dot-filesシンボリックリンクの実体である `dot-claude`・`dot-files` は `additionalDirectories` に登録済みのため、単独 `cd` で移動して素のコマンドで作業できる
* CWD外のリポジトリでの作業を依頼された場合、この制約を理由に依頼を断らないこと。制約は手段の選択に関するものであり、以下の優先順位で手段を選ぶ
  1. ファイルの読み書きだけで済む場合は、絶対パスで Read/Edit/Write を使う（ファイルツールはCWDに依存しない）
  2. git/ghなどのコマンド実行が必要な場合は、以下から状況に最適なものを選択する。いずれの場合もユーザーに操作を投げっぱなしにせず、できる限り自身で実行すること
     * `/add-dir <パス>` の実行をユーザーに依頼する。そのセッション限りで扱う場合に適する
     * `permissions.additionalDirectories` への追加を提案する。今後も繰り返し扱う場合に適する
     * `herdr` skillに従い、対象リポジトリをCWDとする新規Claudeセッションを別workspaceまたは別paneで立ち上げる。セッションの起動からプロンプトの投入まで自身で実施する。作業量が多い場合や、現セッションのコンテキストを保ちたい場合に適する
     * `cd <絶対パス> && git ...` の形式で一時的に移動する。単発のコマンドで済む場合に適する

### 文章とスキル

技術文書（例：ADR、Confluence、JIRA、Pull Requestのdescription、GitHub Issues）、スキル、その他の日本語文章を記載するとき以下に注意すること

* 文章の書き方は `tech-writing-style` Skillに従うこと
* 書き上がったら `sanitize-artifacts` Skillで確認すること
* 会話の経緯や指示の言い回しが成果物に残っていないかを見ること
* 基本原則・方針・判定基準を書くように心がけ、変化しやすい固有名詞や個別事例の列挙は避けること。今後同じ文章を更新するとき、変更が複数箇所に波及しないかを確認する。
* markdownファイルを修正して依頼者にレビューを求める場合は、`mo <ファイル>`（[k1LoW/mo](https://github.com/k1LoW/mo)）でブラウザにライブリロード表示して確認してもらう選択肢がある旨を添えること

### コードコメント

* 以下の例外を除き、コードコメントを書かないこと
* 例外としてコメントを書くときは、書き上がったら `sanitize-artifacts` Skillで確認すること
* 実装意図を後世に伝える必要があると判断した場合は、GitHub PRの行コメントを使うこと（「IssueとPull Request」を参照）。

#### 例外：コードコメントを書いて良い場合

* リポジトリやlinterの指示・慣習に従う場合
* プロンプトで明示的にコードコメントをするよう指示された場合

### 実装計画

実装計画（planファイル）を作成するとき以下に注意すること

* 保存先はリポジトリ内の `docs/plans/` とする（plan modeの場合は `plansDirectory` 設定が同じ場所を指しているが、plan modeを使わずに計画を書く場合も同様にすること）
* ファイル名は `YYYY-MM-DD-<feature-name>.md` 形式とする
* planファイルは実際のソースコード変更と同じPRに含めること。計画だけを先にmergeしない
  * ただし実装規模が大きく複数PRに分かれる場合は、planファイル単独のPRとしてもよい
* planファイルは必ずcommitすること。untrackedのままだと `git worktree add` した先に付いてこず、worktreeでの実装時に参照できなくなる
* planに実装コードを貼らないこと。書いてよいのは、作成・変更するファイルの一覧、作業順序、検証手順、詰まりそうな箇所とする
* planに決定理由を書かないこと。ADRがあればリンクするだけにする
* ADRを書くほどでない規模の場合は、planの冒頭に理由を数行書き、ADRは作らない
* ADRは決定に恒久的な帰結があるときだけ書くこと。ADRに実装手順は書かない
* ADRはADRのみでPR化し、レビューとmergeを経てから実装に着手すること。planファイルとは逆で、ADRだけを先にmergeしてよい（方針が固まる前に実装を進めると手戻りになるため）
* 実装の過程で書くdocs（設計メモなど）は、実装そのものと同じcommitに含めること

### IssueとPull Request

IssueやPull Requestを作成するとき以下に注意すること

* titleとdescriptionの言語は、リポジトリが `karia/` 配下なら全て英語で統一する。それ以外（特にOrganization配下）は日本人がレビュアーであるため、特別な指示がなければ日本語で記述すること
* Pull Requestの作成手順（テンプレートの探索・記入、作成後のURL確認など）は `pr-flow` Skillに従うこと
