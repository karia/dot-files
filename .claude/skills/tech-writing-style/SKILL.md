# 日本語技術文書の文章規範

日本語で技術的な原稿（書籍の章、記事、解説文）を書く・推敲するときは、以下に従う。

## 基本規範（原典）

整形・段落と論証の構成・論証の厳密さ・読み手の負荷の管理・視点と語り・演出の抑制・LLM っぽい表現の禁止・冗長の排除・見出しの付け方・読者への誠実さの各規範は、[references/japanese-tech-writing-source.md](references/japanese-tech-writing-source.md) にローカル保存している。作業前にこのファイルを読み込み、その規範に全面的に従う。

原典は後述の出典（k16shikano 氏の gist）の生内容であり、gist に更新があれば追随できるよう、加工せずそのまま保存している。以降のセクションは、原典に対する独自の追加規範である。

## 文体と表記

- 一つの文書内で敬体（です・ます）と常体（である・だ）を混在させず統一する。ADRのような「決定の記録」の性格を持つ文書は常体を基準とし、既存の同種文書（同じディレクトリの初号ADR等）にスタイルがあればそれに合わせる。
- 略称を用いず正式名称で表記する。単純に表記揺れを防ぐ目的のほか、読み手が推測せず一意に解釈できるようにする。
  - 例：AZ名を「1a」とせず`ap-northeast-1a`と書く。`Open Search`ではなく公式表記に従い`OpenSearch`と書く。
- 金額はMarkdownで通貨記号`$`を使わず`USD`表記に統一する（例：「USD 1,285」）。`$`はMarkdownや数式表示で崩れるため。
- 日本語表記のスタイルはtextlint-rule-preset-JTF-styleの指摘を参考に修正する。実行方法は以下の通り。

```bash
npx -p textlint -p textlint-rule-preset-jtf-style textlint --no-textlintrc --preset jtf-style (document_path)
```

### 日本語と英数字の間のスペース有無

日本語と英数字の間にスペースを入れないスタイル（いわゆる「詰め書き」）にするかどうかについては、以下のガイドを参考にする。

- 文書全体を「日本語と英数字の間にスペースを入れる」「入れない」どちらかの方針で統一するようにする。
- 以下の様にスタイルの指定がある場合はそれに従う。
  - GitHubリポジトリのCI/pre-commitでtextlintなどのlinterが導入されている場合
  - CLAUDE.mdで指示がある場合
- 判断できない場合はユーザーに選択肢を提示し指示を仰ぐ。

- いわゆる「文章のLLM臭さ」を消すためには、「日本語と英数字の間にスペースを入れない」方が望ましい。
- 以下のガイドラインを参考にし、必要に応じて判断材料としてユーザーに提供する。
  - テキストの検索性の観点（たとえば`3日目`をキーワードで検索した場合に、`アドベントカレンダー 3 日目です`表記のテキストはヒットしない場合がある）から、プレーンテキストでは日本語と英数字の間に半角スペースを入れないほうが望ましい。
  - HTMLで文書を描画する場合、CSSに`text-autospace: normal`を指定することで、半角スペース挿入がなくとも、日本語と英数字の間に適切なアキが設定され、読みやすい文書となる。
  - しかし、`text-autospace: normal`の指定がない等で日本語と英数字の間に適切なアキが設定されない場合（GitHubやテキストエディタ等）、半角スペースで調節したほうが読みやすいケースがある。
- 詰め書きにする場合
  - 英単語同士の間（`Michael Nygard`・`sync MTG`）、見出しの番号区切り（`### (1) ADRとは`）、Markdownのリスト記号（`- ` `1. `）のスペースは残す。

## 読者水準

- エンジニア向けの記述としてよいが、当該要素の初心者に伝わる内容で書く（例：DynamoDBやOpenSearchといった基本的単語は理解しているが、アーキテクチャの深部までは理解していない読者）。

## 構造化

- テンプレートがない文書では、重要な内容や要約を先頭に書く。
- 長い本文をベタ書きせず、見出し（H2以降）でセクション分割する。h3・h4 のサブセクションも積極的に活用し、階層で見通しを良くする。
- 表・箇条書きでも構造化する。特に前提条件・対象一覧・比較・コストなどの構造化データは表にする。
- 注釈や短い補足は、Markdownのアラート記法やConfluenceの情報パネルで整理する。これは原典「整形」の「本筋から一段外れる補足は脚注に降ろす」に対応し、パネルや展開が脚注の代用になる。
  - 配置は内容で分ける。前提を先に伝える事前注釈は本文より上に置いてよいが、用語定義など本筋から外れる補足は本文より下に置く。
- 本文から脱線する詳細は、折りたたみ（Markdownの `<details>` タグ、Confluenceの展開など）に収め、本文全体を短く保つことを意識する。

### 表

- 表の一つの列（カラム）には一つの要素だけを入れる。
- 列の中でかっこを使わない。かっこが必要になったときは、列を分割する。欄外注記を指す記号は例外とする。
- 一つのセルに二つ以上の要素が入るときは、列を分割するか、表自体を分割する。
- 「その他」「備考」列を安易に作らない。そこに入るのは通常は書かなくてよい要素であり、削るか、独立した列・表として立て直す。
- セル内に補足を詰め込まず、（注1）や（※）などの注記記号で欄外へ逃がす。
- 表には直前または直後のいずれかに見出しかキャプションを必ず付け、何の表かをひと目でわかるようにする。キャプション記法が使えないツール（例：Confluence）では、表の直上に h3・h4 などの見出しを置く。
- 単位表記の有無は列単位で統一する。数値のみの列では見出しに単位を書き、セルは数値だけにする。同一列で単位を混在させない。
- 仕上げに各行の粒度が揃っているか確認する。粒度が異なる行が混ざるときは、分割・統合・削除・別表化・注釈化のいずれかで整える。

### 箇条書き

- 箇条書きの2段目・3段目のネストを活用し、階層を示して読みやすくする。
- 箇条書き内でかっこの利用はなるべく避ける。かっこを使いたくなったら、その内容は別項目に分けるべきサインであることが多い。ただし「（例：●●）」のような短い例示は除く。

## 手順の書き方

手順書（skill、ランブック、READMEの操作手順）を書くときは以下に従う。

- 読み手がその場で実行できる動作として書く。述語だけで何をするかが決まるよう、「読む」「選ぶ」「確かめる」のような具体的な動詞を使う。
- 推奨される行動を先に書く。制約やできないことは、手順を示した後に置くか、落とし穴をまとめた表へ逃がす。
- 操作を先に、結果を後に置く。コマンドの出力例は、そのコマンドを示した後に置く。
- 例は通常のケースを示す。例外や縮退した状態は、通常のケースを示した後に添える。

### 網羅性と記述量の自己レビュー

書き上げた手順は、「網羅性9割」かつ「記述量最小」になるよう、次のサイクルで見直す。

1. 読み手が置かれる状況をパターン出しし、大多数のパターンが網羅された記述になっているかを検討する。
2. 1を押さえつつ局所最適にしない。大多数が網羅され、かつ最も記述量が少ない書き方になるよう見直し、書き直す。
3. 大多数から漏れる残り1割の例外は、本文に入れ込むか本文外に記述するかを、記述量が少なくなる方で決める。

## 見出し

- 見出しの中に補足を書かない。補足を入れたくなったら、その見出しが内容を言い表せていないサインである。見出し自体を、補足なしで内容が伝わる表現に見直す。

## リンクの置き方

- リンク（出典・参照）は本文での参照箇所の直後に置き、読者がその場で辿れるようにする。
- 末尾に参考文献一覧としてまとめない。ページ内を往復させることになり、末尾の一覧は読まれにくいため。

## AWS 技術文書

- AWS系の技術文書（アーキテクチャレビュー、Well-Architectedレビュー、AWS関連のADR等）を扱うときは、Well-Architected系のスキル（`wa-review`・`architecture-decision-record`・`security-assessment`・`cost-optimization-review` など）も併用する。
